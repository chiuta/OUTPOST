How the listening works

OUTPOST runs entirely in your browser. There's no server behind it, so it can't read a site's real HTTP status the way a proper monitoring service can — a page can only ask another origin "did anything answer," not "what did it say." Each check listens for three independent signals:

  1. A HEAD request with CORS disabled. The browser can't read the reply's contents, but it knows whether one arrived at all. Outright silence — DNS failure, refused connection, timeout — is the strongest evidence something's actually wrong.
  2. A probe for the site's favicon. Loads if the origin answers, fails if it doesn't. On its own this is unreliable — plenty of live sites simply have no favicon.ico at that exact path — so it only ever backs up signal one, never overrides it.
  3. An optional DNS lookup (off by default; switch on "DNS signal"), via Cloudflare's public DNS-over-HTTPS resolver — which means each hostname you watch is sent to Cloudflare — — the only way a browser page can ask "does this domain even resolve," which is otherwise invisible to JavaScript. This is a genuinely different question from "did the server answer": a domain that won't resolve points at DNS or registration trouble, not a crashed web server, and OUTPOST says so specifically when that's what happened. It depends on a third party being reachable, so it's cached for five minutes per domain (to be light on a free public resource) and fails open — if Cloudflare is blocked, offline, or rate-limits the request, this signal is simply left out rather than guessed at. Turn it off in settings any time.

A single reading marks CONTACT if either of the first two signals gets through, SILENT if both fail outright, FAINT if neither resolves cleanly. The displayed status waits for confirmation, though: "Confirm after" sets how many consecutive non-CONTACT readings are needed before a station is actually shown as SILENT — recovery is always immediate, only bad news waits, so one flaky request doesn't cry wolf.

Each station tracks confirmed outages as episodes (start, end, duration), dated from the first raw reading that went wrong rather than the later moment OUTPOST became confident — so the timeline reflects what happened, not the confirmation delay. Resolved episodes get a "copy report" button for a plain-text summary to paste into a ticket or log. If several stations go quiet in the same batch, a banner suggests the more likely explanation is this end of the connection — network, DNS, browser — not every site failing at once; that's a heuristic based on the fraction of stations affected, not a certainty, especially with only a handful of stations logged.

When you switch on the optional canary (off by default), each check batch also pings two well-known, unrelated, extremely-reliable sites (Google, Cloudflare) — your IP address is therefore visible to them — as a canary — the same idea an operating system uses to tell "no internet" from "you're fine." When several stations go quiet at once, the canary turns the correlation banner from a guess into evidence: if it also can't get through, the trouble really is on this end; if it answers fine, the affected stations more likely have a real, if coincidental, problem of their own.

An ongoing outage that has happened to a station before gets a light, clearly-labeled estimate — "typically back within Xm" — averaged from that station's own past resolved outages. It's a pattern, not a promise. Each station also carries a 30-day budget figure: time-weighted (actual outage duration, not a ratio of sampled checks) against a target uptime you set in "Target" — how much downtime is left before that target is blown for the month, or by how much it already has been.

Share status page writes a separate, static, read-only HTML snapshot of the current watchlist — no script, no storage, nothing live — that can be uploaded anywhere to show others what OUTPOST last saw, without handing them the monitoring tool itself. It won't update on its own; re-export when you want a fresher one. Both it and a copied incident report carry a SHA-256 hash of their own content, computed with the browser's native Web Crypto — a way to prove later that a report or snapshot wasn't edited after the fact. That needs a secure context (this file served over HTTPS, or opened from localhost); under plain HTTP or a raw file:// path the hash is simply left off rather than faked.

Two stations that resolve to the same IP address get flagged as likely sharing infrastructure — reusing the DNS lookups already being made, no extra requests. If they're the same box or sit behind the same proxy, an outage in one probably isn't a coincidence when the other follows. When auto-listen is on, a station caught between a failed raw reading and confirmation gets rechecked within about 20 seconds instead of waiting out the full interval, so a real problem gets confirmed — or a blip gets forgiven — faster, without polling settled stations any harder.

Each station also has a spot for your own runbook notes — who to call, what to restart, where to look. Written once, it opens on its own the moment that station actually goes quiet. Each individual outage can separately carry a short cause note — what actually happened this time, distinct from the standing runbook guidance — added while it's ongoing or any time after, and folded into that outage's copied report and escalation email. An ongoing outage can be acknowledged to pause its repeating reminders specifically — lighter than scheduling maintenance, for "I've seen this one, stop nudging me about it" without silencing anything else. Quiet hours mute the sound and browser notification for status changes during a time window you set — the toast, the trace, and the station's own status still update as normal, only the audible/push alerting is held back.

If local storage ever stops accepting writes — full, or disabled by the browser (private browsing sometimes restricts it) — a banner says so plainly instead of failing silently. Everything keeps working in this session; it just won't survive closing the tab until storage is available again.

Buttons and selects are sized for a thumb, not just a cursor — the check and remove icons in particular, since a mis-tap on "remove" is the one action here that isn't undoable. Add this page to a phone's home screen and it launches full-screen, without browser chrome, using its own icon.

The uptime figure on each card is a 24-hour, time-weighted number once there's enough elapsed time to compute one — actual downtime duration within that window, the same basis competitors' dashboards lead with, rather than a coarser ratio of however many checks happened to land during an outage. Hover it for the 7-day figure too; the 30-day budget stat already covers the longer window.

Stations can carry a category — Personal, Work, Projects, Organizations, or anything typed in — which groups the list into collapsible sections and can be filtered down to just one. A category with enough stations to need it can carry a subcategory too, nested one level inside — a station without one still sits directly in its category, unindented, so a small category never grows a pointless empty sub-section. A station can separately carry which server hosts it — a different axis from category (what it's for vs. what it's on) — and the "Group by" control switches the whole list between the two views without touching either field. Maintenance windows (30 min to indefinite) freeze the parts of OUTPOST that would otherwise treat planned downtime as a real incident: no episode opens, no notification fires, and the time is cut out of the 30-day budget and the correlation count entirely. Checks still run underneath, so the data keeps flowing — only the interpretation pauses.

Remind me repeats the alert on an interval for as long as a station stays confirmed down, instead of the one notification on the initial transition going unnoticed if you're away from the tab — mirrors the "resend interval" idea from other monitoring tools. Off by default. Each station also has a svg badge download — a small, shields.io-style status badge sized to actually embed in a README or a personal page, distinct from the full status-page snapshot. Both it and the status page reflect a station's maintenance state rather than showing planned work as a real outage.

Modeled in part on what self-hosted and commercial uptime tools (Uptime Kuma and its competitors) tend to offer. A few of their standard features don't survive the trip to a client-side, no-server tool and are left out on purpose rather than faked: reading a certificate's expiry date requires a raw TLS handshake browsers don't expose to page scripts, and no free, keyless API fills that gap the way Cloudflare's DNS resolver does for the DNS signal; checking from multiple regions would require routing through third-party proxy servers OUTPOST has no way to vet; and matching keywords inside a page's content is blocked by the same opaque no-cors response that makes the reachability check itself possible in the first place.

Reopen this file after being away for a while and, if anything happened, a dismissible panel reconstructs it from the outage log itself — no separate tracking, just reading back through episodes that started after the last time this tab was active. The browser tab's title and icon also carry a live trouble count, so a glance at the tab bar is enough without switching over.

Once there are enough stations that a flat list stops being scannable, Health gives each one a single 0-100 number — 70% current confirmed status, 30% historical uptime, with small penalties for a worsening latency trend or a blown budget — and Sort/Show let the list order by it (worst first, by default) or by latency, name, or recency, and optionally hide anything that isn't currently in trouble.

Every outage — ongoing or resolved — has an email button alongside "copy report" that opens a pre-filled message (subject, timing, duration, and any runbook notes for that station) with the recipient left blank on purpose, since OUTPOST shouldn't guess who the right person to tell is.

Shortcuts: L listens now, / jumps to the add field, E exports — all inactive while typing in a field.

What none of this can do:

  • Tell a 500 error from a 200 OK — only whether the server responded, not what it said.
  • Check a plain-HTTP site from a page served over HTTPS — the browser blocks that outright as mixed content. Open this file over HTTP or as a local file to listen to HTTP-only stations.
  • Keep listening while the tab is closed or backgrounded for long — browsers throttle timers in inactive tabs, so auto-listen is no substitute for real server-side monitoring.
  • Notice when a CDN or edge server answers on behalf of an origin that's actually down.

Everything — the station list, the full check log, episodes, your settings — stays in this browser's local storage. Nothing is sent anywhere except the reachability checks to the stations you add (each station sees your IP address, like any visitor, and also gets a request for /favicon.ico) and, only if you switch them on, DNS lookups to Cloudflare's resolver and the Google/Cloudflare canary. "Contact" means only that something answered at the network level — an error page (404, 500, 502) also counts as Contact. The exported log contains your station list, notes and last-seen IP addresses: treat it as private. Export the log any time to back it up or move it to another browser; if this file is open in two tabs at once, they stay in sync automatically.
